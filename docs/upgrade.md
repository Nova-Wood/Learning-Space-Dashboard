# 升级与验收

## 部署顺序

1. 备份原 Supabase 数据库和旧部署配置，在测试项目先验证。
2. 若已有习惯表，检查重复日期：

```sql
select date, count(*) from public.daily_routines group by date having count(*) > 1;
```

旧环境无该表时跳过，迁移会创建。若有重复日期，人工核对并合并；迁移会报错回滚，**不会自动删除记录**。

3. 填写 `APP_PASSWORD`、`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`，安排维护窗口。旧代码用 anon key，收紧权限后旧版会暂时不可用。
4. SQL Editor 执行 `supabase/migrations/001_reliable_workspace.sql`，确认整段提交成功。
5. 部署新版，检查登录和历史数据读取。
6. 按 `google-calendar.md` 完成授权；未配置日历不影响其他模块。

## 验收清单

- 不登录不能访问；原 URL 密码入口失效；退出后不能继续操作。
- 更新习惯后刷新，仍是同日同一条记录。
- 开始专注后另一设备刷新可见；结束后只有一组日志且计时关闭。
- 往年同月数据不进入本月；跨午夜的新日志分别计入两天。
- 笔记无需“读完”即可保存，完成的任务可以恢复。
- 空记录时仍能生成和反复下载日报。
- Google 日历列出已有事件；用户主动创建测试日程后 Google 端可见。
- 匿名 API 角色不能读写业务表，服务端角色可操作。

## 数据与回滚边界

- 保留旧表和数据，新增 session_id、索引、约束和 RPC，不重新分配历史跨日记录。
- 正在计时的旧记录获得 session_id；旧时间须为 `YYYY-MM-DD HH:MM:SS`，异常历史值需人工修正。
- 新约束以 NOT VALID 添加，不强制旧记录立刻通过；修改不合格历史行时会拒绝，应先修正空标题等问题。
- 不自动撤销权限，避免重新暴露数据库。故障时优先回滚到仍使用服务端密钥的版本，或维护状态下修复。
- 不自动执行生产 SQL，不自动合并 PR。数据库和 Google 实际联通以部署验收为准。
- 多人演进需引入 Supabase Auth、每表 user_id 和逐用户 RLS；单人场景可在入口加平台访问限制或网关限流。
